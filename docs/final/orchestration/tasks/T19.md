## 1. Either control scheme (#55)

In human vs AI (pygame `--versus`, hosted page `mode=ai`) and online, both key sets drive the player's own seat: WASD, F, G, T, left Shift **and** arrows, `.`, `/`, `'`, right Shift. Pressing keys from both sets at once combines them as held keys of one seat. Local two-player on one keyboard keeps seat A = WASD set, seat B = arrows set. Key hints say so.

## 2. Input grace window (#54)

Reproduce first: write a failing test that shows `left` then `up` one tick apart (and `up` then `left`) gives a plain move and then a late or lost jump today. Then fix it so that a direction and a jump pressed within **2 ticks** of each other, in either order, give one directional jump (a flip, #53) in that direction, and a press made during a move's last frames is buffered and starts when the move ends. A single direction press alone must not get slower than today by more than the window, and the report states the added latency exactly. Choose the mechanism (input-layer buffer, or an engine rule that lets a move started in the last 2 frames turn into a jump), and justify it:
- If it is an engine rule, it gets a new `RULE_SOURCE_MAP.md` row (`design`, Saad #54), a failing test first, and it applies to every seat the same way (AI seats go through the same `engine.step`).
- If it is input-layer only, one shared implementation is used by `play.py`, `web/bridge.py` (hosted page) and `server/match.py`; no front end keeps its own copy.
Determinism holds: no wall clock in the decision, only tick counts.
